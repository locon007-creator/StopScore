## Binding HTTP Contract for Task 2/3

- `GET /api/v2/workday` → `{ workday: WorkdayAggregate | null }`.
- `POST /api/v2/workday`, `Idempotency-Key` header:
  - Start body: `{ action: "start", equipment, stops }`; returns `{ workday }`, status 201.
  - Finish body: `{ action: "finish", workdayId }`; returns `{ workday }`, status 200.
- `POST /api/v2/stops/:stopId/events`, `Idempotency-Key` header:
  - Body: `{ action: "navigate" | "arrive" | "depart" }`; returns `{ workday }`.
- `POST /api/v2/stops/:stopId/experience`, `Idempotency-Key` header:
  - Body: `{ scores: { yard, staging, staff, waitingTime, bathroomAccess }, waitingCategory }`; returns `{ workday }`.
- Errors use `{ error: { code, message } }` and map validation 400, unauthenticated 401, missing 404, conflict/stale 409, and unexpected storage 500. The 500 message is always generic.
- Authentication is awaited before write body parsing or repository creation. Driver email is normalized and scopes every service/repository operation.
- Client stop `id` values are discarded. Persisted IDs are generated by the service and scoped under the generated workday ID.
- `activeStopIndex` is returned by the server and advances only inside the atomic experience-publish commit.

## Domain and State Behavior

- Canonical equipment: `tractor`, `bobtail`, `straight_truck`, `cargo_van`.
- Tractor trailer types: `dry_van`, `reefer`, `flatbed`, `step_deck`; trailer type is required and trailer number remains optional, matching the recovered Equipment Information contract.
- Stop types: `delivery`, `pickup`, `drop_hook`, `delivery_pickup`.
- Experience topics are locked in order: `yard`, `staging`, `staff`, `waitingTime`, `bathroomAccess`; every score is an integer 1–5.
- Waiting categories: `quick`, `standard`, `long`, `extremely_delayed`.
- Provider IDs must exactly match `osm:(node|way|relation):[1-9][0-9]*`; fabricated identities, zero, leading zeroes, signs, and decimals fail before a repository write.
- Legal transitions are `pending → navigating → arrived → departed → experience_published`.
- Finish requires every stop to be `experience_published`.

## Atomicity and Idempotency

- D1 start uses one `batch()` for workday, stops, and idempotency record.
- Event/publish batches begin with `INSERT … SELECT` statements carrying driver, active-workday, active-stop-index, and expected-state SQL preconditions.
- The exact `activeStopIndex` read into the response aggregate is also bound into the SQL precondition, so an adjacent operation that advances between read and batch conflicts instead of committing a stale response/idempotency snapshot.
- Later mutations are conditional on the inserted event/experience sentinel ID. A failed precondition therefore inserts no event/experience and changes no stop/workday state.
- Finish uses a conditional update requiring no unpublished stop.
- Replays return the aggregate stored with the committed idempotency record. Concurrent identical requests perform a post-batch replay lookup so both callers converge on the same committed aggregate without duplicate rows.
- Reusing the same key for a different operation returns conflict.
